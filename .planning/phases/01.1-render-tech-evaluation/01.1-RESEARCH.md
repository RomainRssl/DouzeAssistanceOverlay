## Summary

The current architecture renders overlays entirely with WPF primitives (TextBlock, Border, Canvas, Polyline, Ellipse, Rectangle) inside a `Window` with `AllowsTransparency=true`. The VR path captures each overlay with `RenderTargetBitmap` (software-only CPU operation), converts BGRA to RGBA manually, then either calls `SetOverlayRaw` (SteamVR path) or uploads pixels via `D3D11Native.UpdateSubresource` into OpenXR swapchain textures (OpenXR path). Both paths do this work on the UI thread at each 60Hz tick.

**The good news for Phase 2:** WPF already handles drag, resize, themes, and 2D/VR profiles natively — `BaseOverlayWindow.cs` already implements all of it (drag, edge handles, Viewbox scaling, UseRawResize, UseWidthOnlyResize, theme change notification, settings persistence). Phase 2 UI requirements (UI-01 through UI-04) are achievable in pure WPF without any render tech change. WPF's limitation is not Phase 2 blocking; it is VR performance (RenderTargetBitmap is software-only and blocks the UI thread, ~0.5ms–5ms per overlay capture at VR resolution).

**The SkiaSharp D3D story is more nuanced than expected:** SkiaSharp 3.119.x includes a **D3D12** backend via `SkiaSharp.Direct3D.Vortice` (preview), **not D3D11**. SkiaSharp's `SKElement` for WPF uses raster/software rendering via `WriteableBitmap` — the same CPU path as the current code. There is no ready-made D3D11 path in SkiaSharp's WPF integration. The most viable "SkiaSharp + D3D11" approach for VR-01 is: render Skia to a CPU bitmap inside `SKElement`, then upload that bitmap to the existing D3D11 texture in `OpenXRService.UploadPixels()`. This is a render-quality improvement (Skia's rasterizer is higher quality than WPF's for small text and subpixel rendering) but not a GPU-acceleration win.

**Primary recommendation:** For VR-01 PoC — wrap the `FuelStrategyOverlay` (or `ProximityRadarOverlay`) in a `SKElement`, draw its contents via SkiaSharp's canvas API, and time the per-frame render cost against the current WPF/RenderTargetBitmap path. Both paths are CPU-bound; the question the PoC answers is whether Skia's rasterizer is faster AND whether the resulting bitmap quality is acceptable for VR. Phase 2 proceeds in WPF regardless of outcome.

## Architecture Patterns

### Current Rendering Architecture (what exists today)

```
DispatcherTimer (60Hz, UI thread)
  └── foreach overlay → overlay.UpdateData()          ← WPF property mutations
  └── vrService.UpdateAll()                           ← VR path
        └── RenderTargetBitmap.Render(content)        ← SOFTWARE CPU capture
        └── CopyPixels → byte[] BGRA→RGBA conversion  ← byte loop, GC pressure
        └── OpenXRService: D3D11Native.UpdateSubresource  ← GPU upload
        └── VROverlayService: SetOverlayRaw           ← SteamVR CPU upload
```

**Key file:** `LMUOverlay\LMUOverlay\LMUOverlay\LMUOverlay\VR\OpenXRService.cs`, method `UpdateAll()` (line 439–472) and `UploadPixels()` (line 569–597).

**Key file:** `LMUOverlay\LMUOverlay\LMUOverlay\LMUOverlay\VR\VROverlayService.cs`, method `CaptureAndSubmit()` (line 210–263).

### The RenderTargetBitmap bottleneck

`RenderTargetBitmap` is **software-only** (confirmed by dotnet/wpf#9021, open as of April 2024). Every VR frame capture is a full CPU rasterize of the WPF visual tree, with a manual BGRA→RGBA byte loop on top. At 512x512px per overlay with 17+ overlays, this is significant UI thread work. Each `RenderTargetBitmap.Render()` call forces a WPF layout pass on the captured visual subtree.

### SkiaSharp WPF Integration: What SKElement Actually Does

`SKElement` is a `FrameworkElement` that:
1. Creates a `WriteableBitmap` (Pbgra32, CPU memory).
2. On each `InvalidateVisual()` call, opens the bitmap's back-buffer, creates an `SKSurface` pointing at it, calls `OnPaintSurface(e)` (where you draw with Skia's canvas).
3. Closes the back-buffer, calls `drawingContext.DrawImage()` to blit the bitmap to WPF's rendering pipeline.

This is **software/raster rendering** — same CPU path as the current code, but using Skia's rasterizer instead of WPF's retained-mode visual tree.

**Advantage of Skia raster over WPF retained mode:**
- Lower GC pressure: Skia draws imperatively into a fixed byte buffer vs WPF creating/mutating visual tree nodes.
- Better performance for draw-every-frame patterns (gauges, radar, graphs) vs WPF's strength in retained/dirty rect updates.
- Higher quality subpixel text rendering and anti-aliasing.

**No GPU win:** Replacing the visual tree with `SKElement` does not eliminate the RenderTargetBitmap step. After `SKElement` draws into its `WriteableBitmap`, the VR path still needs to snapshot it. However, you can replace the `RenderTargetBitmap.Render()` + `CopyPixels()` with a direct `WriteableBitmap.CopyPixels()` on the `SKElement`'s bitmap — which is faster because the bitmap is already in the correct format and the data is already in CPU memory without a layout re-render.

### PoC Architecture: SkiaSharp + D3D11 on One Overlay

"D3D11 backend" in the context of this project's VR pipeline means: **Skia draws to a CPU bitmap, which is then uploaded to the existing D3D11 texture via `UpdateSubresource`** — the same mechanism already in `OpenXRService`. The D3D11 device already exists.

**True GPU-accelerated Skia path** would require `SkiaSharp.Direct3D.Vortice` (D3D12, preview, not D3D11) or a custom ANGLE/OpenGL context. This is too risky for a PoC evaluation and conflicts with the existing D3D11 device in `OpenXRService`.

**Recommended PoC approach (VR-01):**

```
[Chosen overlay — e.g. FuelStrategyOverlay]
  ├── Add SKElement child alongside or replacing the existing WPF canvas content
  ├── Override UpdateData() to call skElement.InvalidateVisual()
  ├── In SKElement.PaintSurface: draw the same data using SKCanvas (imperative drawing)
  └── In VR path:
        ├── Instead of RenderTargetBitmap.Render(content) + CopyPixels
        └── CopyPixels directly from SKElement's WriteableBitmap back-buffer
            → BGRA→RGBA byte swap → D3D11Native.UpdateSubresource (existing path)
```

**PoC overlay choice — `FuelStrategyOverlay`:** It contains text, bars, a grid layout — representative of the most common overlay type. It is not the most complex graphics-wise (ProximityRadar or InputGraph use Canvas with dynamic children) making it a fair baseline.

### Alternative: ProximityRadarOverlay as PoC

Better for measuring Skia drawing performance because the radar uses dynamic `Canvas.Children` manipulation every frame (adds/removes Rectangle elements), which is the highest WPF retained-mode overhead pattern. Replacing this with a single `SKCanvas.DrawRect()` loop should show the largest frame-time improvement.

### Anti-Patterns to Avoid

- **Do not use `SKGLElement` (OpenGL path):** It requires `WindowsFormsHost` which is incompatible with `AllowsTransparency=true` overlay windows (airspace problem — WPF transparent windows cannot host HwndHost children). The window would become invisible.
- **Do not add `SkiaSharp.Direct3D.Vortice` to this project:** It introduces a D3D12 hard dependency. As of SkiaSharp 3.116+, `libSkiaSharp.dll` already has a link-time dependency on `d3d12.dll` — adding the Vortice D3D12 package on top increases this risk for VR evaluation.
- **Do not redesign `BaseOverlayWindow`:** The PoC only affects one overlay's internal rendering. `BaseOverlayWindow` remains a WPF `Window` — this is intentional; SkiaSharp is evaluated as a rendering backend inside the existing window host.
- **Do not mix SkiaSharp rendering with WPF children in the same overlay for the PoC:** Either draw everything in Skia or keep everything in WPF. Mixing adds complexity that obscures the benchmark signal.

## Common Pitfalls

### Pitfall 1: Assuming "D3D11 backend" means GPU-accelerated Skia rendering

**What goes wrong:** The VR-01 requirement says "SkiaSharp 3.119.2 + D3D11 backend." This could be interpreted as running Skia's GPU rasterizer on the D3D11 device, which would eliminate CPU rendering entirely.

**Why it happens:** SkiaSharp's documentation shows GPU backends (GRContext). The existing OpenXRService already has a D3D11 device (`_d3dDevice`). It seems natural to connect them.

**Reality:** SkiaSharp's GPU backends are **OpenGL (via ANGLE)** and **D3D12 (via Vortice, preview)**. There is no stable D3D11 GRContext. Using the D3D11 device for Skia GPU rendering would require either: (a) custom ANGLE integration, or (b) the Vortice D3D12 package (which requires a separate D3D12 device, not the existing D3D11 one).

**How to avoid:** Interpret "SkiaSharp + D3D11 backend" as: Skia draws to a CPU bitmap; that bitmap is uploaded via the existing D3D11 UpdateSubresource mechanism. This is the only viable D3D11 path.

**Warning signs:** If the PoC design requires a second GPU device, or requires `GRContext.Create()`, you've gone off-path.

### Pitfall 2: SKElement inside a `AllowsTransparency=true` window

**What goes wrong:** `SKElement` extends `FrameworkElement` (pure WPF), so it is compatible with transparent windows. But `SKGLElement` uses `WindowsFormsHost` internally and will produce a black/invisible rectangle in an `AllowsTransparency=true` window.

**How to avoid:** Use `SKElement` only. Never use `SKGLElement` for overlay windows.

### Pitfall 3: New RenderTargetBitmap created per frame in OpenXRService.UpdateAll()

**What goes wrong:** `OpenXRService.UpdateAll()` (line 455 of OpenXRService.cs) creates a **new** `RenderTargetBitmap` on every frame, unlike `VROverlayService.CaptureAndSubmit()` which reuses `inst.CachedRtb`. This means per-frame GC allocations in the OpenXR path.

**Why it matters for the PoC:** When benchmarking the current path, measure the OpenXRService path (which allocates) vs a SkiaSharp path (WriteableBitmap is stable and reused by SKElement). The benchmark will show an outsized win for Skia partly due to this existing allocation bug, not just rendering speed.

**How to avoid:** Note this bug explicitly in the PoC report. Fix it in the comparison baseline if a fair benchmark is needed (use the VROverlayService cached-RTB pattern as baseline, not the OpenXRService allocating pattern).

### Pitfall 4: SkiaSharp 3.119.x has a link-time D3D12 dependency

**What goes wrong:** Adding SkiaSharp 3.119.2 to the project pulls in `libSkiaSharp.dll`, which links to `d3d12.dll` at load time. On Windows 10 machines without DX12 (older GPUs), the application crashes immediately on startup — before any SkiaSharp code is called.

**Impact:** ~0.1% of Windows installs as of mid-2024. For a sim racing app where hardware ranges widely, this is a real risk.

**How to avoid:** The PoC should test on the target hardware. Document this risk in the recommendation. If SkiaSharp is adopted, require Windows 10 1703+ (Creators Update) as minimum, which ships D3D12.

### Pitfall 5: Benchmarking on the UI thread at 60Hz hides actual cost

**What goes wrong:** The DispatcherTimer fires at 60Hz on the WPF UI thread. Measuring "time per frame" on the UI thread will show low numbers if the renderer is slow, because the timer will simply skip late callbacks — you won't see the actual backlog.

**How to avoid:** Use `Stopwatch.GetTimestamp()` before and after the render call within `UpdateData()`. Log the per-call duration to a `Queue<long>` and report min/avg/max/P95 over a 500-sample window. This reveals true render cost, not timer firing rate.

## Code Examples

### SKElement Integration Pattern in a WPF Overlay

```csharp
// Source: https://github.com/mono/SkiaSharp (SkiaSharp.Views.WPF)
// Add this as Content inside the overlay's Border, replacing the existing visual tree

using SkiaSharp;
using SkiaSharp.Views.WPF;

public class FuelStrategySkiaOverlay : BaseOverlayWindow
{
    private readonly SKElement _skElement;
    private FuelData _lastData;     // updated by UpdateData(), read by PaintSurface

    public FuelStrategySkiaOverlay(DataService ds, OverlaySettings s) : base(ds, s)
    {
        _skElement = new SKElement();
        _skElement.PaintSurface += OnPaintSurface;
        Content = _skElement;      // SKElement IS a FrameworkElement — compatible with transparent window
    }

    public override void UpdateData()
    {
        _lastData = DataService.GetFuelData();
        _skElement.InvalidateVisual();  // triggers PaintSurface on the UI thread
    }

    private void OnPaintSurface(object? sender, SKPaintSurfaceEventArgs e)
    {
        var canvas = e.Surface.Canvas;
        canvas.Clear(SKColors.Transparent);

        using var paint = new SKPaint
        {
            Color = SKColors.White,
            TextSize = 14,
            IsAntialias = true
        };
        canvas.DrawText($"{_lastData.FuelToAdd:F1} L", 10, 30, paint);
        // ... rest of drawing
    }
}
```

### Frame Time Measurement Pattern

```csharp
// Measure per-call render cost inside UpdateData()
private readonly Queue<long> _renderTimes = new(500);
private static readonly long _freq = System.Diagnostics.Stopwatch.Frequency;

public override void UpdateData()
{
    long t0 = System.Diagnostics.Stopwatch.GetTimestamp();
    // ... actual rendering ...
    long t1 = System.Diagnostics.Stopwatch.GetTimestamp();

    long us = (t1 - t0) * 1_000_000L / _freq;   // microseconds
    _renderTimes.Enqueue(us);
    if (_renderTimes.Count > 500) _renderTimes.Dequeue();
    // Report: avg, p95, max
}
```

## Open Questions

1. **Is WPF retained-mode rendering already fast enough for 60Hz VR with 17+ overlays?**
   - What we know: RenderTargetBitmap is software-only, creates layout re-renders. VROverlayService caches the RTB. OpenXRService does not (allocation bug).
   - What's unclear: Actual per-frame cost on the target machine. Has not been profiled.
   - Recommendation: **Measure first.** The PoC should include a baseline measurement of the current path before building the Skia alternative.

2. **Does SkiaSharp's D3D12 link-time dependency in libSkiaSharp.dll affect this project?**
   - What we know: SkiaSharp 3.116+ links to d3d12.dll at load time. 0.1% crash rate in production apps.
   - What's unclear: Whether LMU sim racers commonly run hardware without D3D12.
   - Recommendation: Document as risk; test on a Windows 10 machine with an older GPU if available.

3. **Which overlay maximizes benchmark signal?**
   - What we know: ProximityRadar adds/removes Canvas children every frame (worst WPF case). FuelStrategy mutates properties (better WPF case). InputGraph uses Polyline + Canvas (intermediate).
   - What's unclear: Which scenario is more representative of Phase 2 requirements.
   - Recommendation: Use **ProximityRadarOverlay** for the Skia PoC — it has the highest current WPF overhead and will show the maximum delta. Then benchmark FuelStrategy as a secondary data point.

4. **Can Phase 2 (drag/resize/themes) be implemented purely in WPF without render changes?**
   - What we know: `BaseOverlayWindow.cs` already implements drag, resize (three modes), theme notification, opacity/background opacity, settings persistence. Phase 2 is about exposing existing capabilities and adding new themes to ThemeManager.
   - Verdict: **YES** — Phase 2 does NOT require a render tech change. This is confirmed by the codebase analysis. The evaluation result for Phase 2 is already determined: stay with WPF for Phase 2 regardless of SkiaSharp PoC outcome.
