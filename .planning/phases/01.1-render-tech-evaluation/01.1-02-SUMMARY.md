## Risk Note: D3D12 Link-Time Dependency (SkiaSharp 3.119.x)

**SkiaSharp 3.119.x includes `libSkiaSharp.dll` which has a link-time dependency on `d3d12.dll`.** This means the application will fail to start on Windows 10 machines without D3D12 support (pre-Creators Update, approximately 0.1% of Windows installs).

- **Impact for this project:** Acceptable — sim racing apps require capable GPU hardware; WMR/SteamVR runtimes also require D3D12. Players running LMU already have D3D12-capable machines.
- **Mitigation if needed:** `SkiaSharp.NativeAssets.Win32` allows selective deployment; alternatively, delay-load the DLL. For this PoC, no mitigation is needed.
- **Do NOT add `SkiaSharp.Direct3D.Vortice`** — that is a separate D3D12 GPU-backend package not used here. This project uses the Skia software rasterizer only (`SKElement` → CPU raster → WPF compositor).

## Note on "SkiaSharp + D3D11" in this Project

The plan research mentions a "Skia raster → existing UpdateSubresource path" for SkiaSharp + D3D11. In the context of this project, this means:

1. `SKElement` renders via Skia's **CPU software rasterizer** into a pixel buffer (no GPU involvement in Skia itself)
2. WPF's `WriteableBitmap` / D2D compositor copies this buffer to the GPU for display
3. For the **OpenXR/VR path** (Phase 01.1 end goal), the Skia pixel buffer would be fed into `OpenXRService.UpdateAll()` via `CopyToBytes()` → `UpdateSubresource()` — replacing the current WPF `RenderTargetBitmap` capture
4. This gives a single CPU→GPU copy path (Skia raster → D3D11 texture) vs. the WPF path (WPF retained mode → RTB capture → D3D11 texture)

The frame-time data from both `[ProximityRadar WPF baseline]` and `[ProximityRadar SKIA]` logs (collected during an actual sim session) will determine whether the SkiaSharp path is faster, slower, or equivalent.
